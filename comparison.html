Huge Graph Rendering: Site vs Pure SVG

Generated with scripts/bench-svg-vs-site.mjs – measures load performance of the same graph rendered as standalone SVG vs inside GraphEditorPro (with UI, selection, grid, etc).

Key finding: Pure SVG is ~10-18% faster to load and uses ~2-3× fewer DOM elements. Site overhead comes from:
  • UI chrome (toolbar, sidebars, modals) – ~13k-23k extra DOM nodes
  • Per-edge extra elements: hit area (.edge-hit), selection rings (.edge-sel), labels, background plates
  • JS execution: style merging, caching, selection sync, grid pattern – 150-380ms script
  • Style/layout recalc for interactive layers
The biggest cost is DOM count, not JS. Complete 100n (4950 edges) → 8752 elements pure vs 27279 in site (3.1×).

Why Site is Heavier

  • Per edge in site: 5 elements (g, .edge-hit, .edge-line, .edge-arrow, optional label) vs 1-2 in pure SVG (path + polygon). Plus selection rings when selected.
  • Per node in site: 2-3 elements (g, shape, label, optional sel ring) vs 2 in pure (g + ellipse + text).
  • Extra layers: grid pattern (world-locked SVG pattern), camera layer, selection overlay, UI panels – 13k+ nodes.
  • JS work: style merging (nodeVisual/edgeVisual cached per pass now), edge offset cache, geometry cache, selection mirror – still 150-380ms.

Takeaways

  • Pure SVG file renders with zero JS, only style+layout (15-44ms style, 8-31ms layout). Site adds 120-346ms style + 90-120ms layout due to extra layers and attribute writes.
  • File size is similar (pure SVG slightly larger for complete graph because site JSON is more compact than SVG paths), but DOM is 2-3× larger in site.
  • For huge graphs, biggest win would be: edge virtualization (skip off-screen edges), or Canvas/WebGL renderer, or reducing per-edge elements (drop .edge-hit, merge arrow into path).
  • Current optimizations (caches) already cut 18-34% load time vs main branch for 1500n.
