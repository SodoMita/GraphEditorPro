# Graph Editor Pro

Graph Editor Pro is an offline graph editor distributed as **one self-contained `index.html`**. It has no runtime dependencies, external assets, dynamic imports, or network requests, so the generated file can be opened directly from disk.

The application is maintained as TypeScript, HTML, and CSS source files. The build compiles and inlines them into the single-file deliverable.

## Development

Requires Node.js 20 or newer.

```bash
npm ci
npm run build       # type-check and regenerate index.html
npm test            # build plus safety, logic, syntax, and DOM smoke tests
npm run typecheck   # TypeScript only
```

CI runs `npm run check` on Node 20 and 22 and verifies that the committed `index.html` matches the build. It also runs `npm run test:browser`, which opens that file offline in headless Chrome and checks keyboard focus with and without native dialogs. To run the browser tests locally, use installed Google Chrome or set `BROWSER_DIR` to the Chromium directory produced by `scripts/browser-setup.sh`.

After a successful build, open `index.html` in any modern browser.

## Resizing the workspace

Drag the shared edge between the canvas and the data area, or between the adjacency matrix and edge list. The existing borders double as resize targets, with the same 32-pixel drag zone on mouse and touch by default. If a pane is hidden, use the view buttons to show it first (in the Data tab on mobile). In **Data → Pane sizes**, enter the canvas or matrix share as a percentage. The fields reflect the current layout after dragging or changing views. Change **Drag zone (px)** to adjust the target thickness, or turn off **Resize by dragging** to use only the numeric size controls. These two preferences are saved in your browser.

## Editing the adjacency matrix

Matrix cells and node labels follow a **select-then-edit** contract: the first press selects (the edges of a cell, or the node of a label) and arms the field, the second press — or a plain double-click — opens its editor. `Enter`, blur, or pressing any other matrix field commits the edit; the commit re-locks every matrix field and clears the armed-field state, so the next single press selects again instead of reopening an editor. The reset covers node-label commits as well as weight commits: a label edit that left the session armed made a later single click reopen the editor while an unrelated canvas selection stayed in force, so selection-based actions could hit the wrong node.

Structural rules keep that interaction stable, all of them covered by `tests/chromium/matrix-cell-edit.test.mjs` and `tests/matrix-edit-state.test.mjs`:

- **Promotion is layout-neutral.** Cells render as lightweight `<td>` text; opening an editor inserts an `<input>` that is absolutely positioned over its cell (with the cell text kept as a hidden width placeholder), so the table never reflows while a cell is edited. An in-flow input contributes its own intrinsic width to the column: the edited cell used to jump sideways and the whole grid shifted under the pointer, which made clicks — and the second press of a double-click — land on the wrong cell.
- **The frozen frame is opaque.** The sticky corner, column headers and row headers all paint a solid background, so cells sliding underneath while scrolling can never bleed through the frozen frame.
- **An open editor owns the pointer.** A press inside the field that is already open is left to the browser (the handler returns before any `preventDefault`), so clicks reposition the caret and drags select text; preventing it used to freeze the caret where `focus()` had put it.
- **Open editors survive matrix rebuilds.** A rebuild replaces `#matrixHost` wholesale, and committing one cell queues a rebuild ~60 ms later — exactly when a fast double-click has opened the next editor. `renderMatrixAndList()` captures the open session (which field, its text and caret, and for labels whether the row-head or column-head instance was open) before swapping the HTML and re-opens it afterwards. The companion trap: Chromium fires `change` on a focused input when a rebuild *removes* it, still reporting `isConnected`; the change handler re-checks connectivity in a microtask so that removal-commit is left to the session restore instead of writing half-typed text into the graph and queueing a second, editor-destroying rebuild.
- **A blur commits what the user typed, and only that.** `change` alone is not enough: an editor re-opened by the session restore gets its text *programmatically*, which clears the browser's dirty flag, so blurring it without typing again fires no `change` at all. The grid then displayed the restored weight while the graph still held the old one, and a reload exposed the loss. So the app tracks the session itself — an `input` listener on `#matrixHost` marks the **field** as holding a draft, opening a field or committing clears that mark, and capture/restore carries it onto the fresh instance a rebuild creates. Per field, not one shared boolean: clicking a node's *other* label instance (row head ↔ column header) opens a new editor before the old field's deferred blur runs, and a shared flag let the new session erase the old one's draft, discarding the typed label. On blur, a draft whose text differs from the values the cell renders from live graph state is committed (a real `change` commit runs first and makes this a no-op), and the session closes like any other commit.
  Inferring "uncommitted" from the graph alone is not safe: re-open a cell without typing, press Ctrl+Z (undo is handled while a matrix field has focus) and tab away, and the editor's stale text is a *difference* from the graph — the blur used to write it back and silently undo the Undo. An untouched session therefore never commits; instead the field is re-set to the model so the demoted cell cannot display a weight the graph does not have. The comparison is display-level — separators folded onto `;`, whitespace trimmed, but **empty values kept and runs of separators not collapsed**, because one entry per edge is what decides how many edges a commit keeps: a cell with a parallel unweighted edge renders `;7`, and reducing it to `7` means "one value for two edges", which drops the extra edge. Filtering the empties away made the two look equal and left both edges in the graph; splitting on `/[;,\n\r]+/` was the same mistake one level down, folding `7;;` (three parallel edges) and `7;` (keep one) into the same string. Node labels mirror the same rules against `label || id`.
- **A restore replays a draft, and nothing else.** Re-opening an editor after a rebuild restores its text and caret when the session holds a draft; when it does not, the field re-reads the model instead, because the graph may have moved while the editor was open (Undo, an algorithm, an import). Committing `42` over `3`, re-opening the cell and pressing Ctrl+Z used to leave `42` in the *focused* editor, so the next keystroke committed `420` instead of editing the undone `3`. For the same reason a commit re-locks every matrix field except a different editor that the closing gesture has just opened, and the armed state it clears is instance-aware — a node's row-head and column-header labels are two fields for one node, and committing one must not disarm the other.
- **A deferred commit never disturbs what the closing gesture did.** The gesture that closes an editor moves the selection *and* arms the field it pressed, both *before* the deferred commit runs. So the commit's own "select the cell I just edited" step used to put the selection back on the edited cell — editing E1 and clicking E2 left E1 selected, and selection-based actions hit the wrong edge — and its unconditional "clear the armed field" reset used to disarm the clicked cell, so switching cells took three clicks (select, select again, then edit). A deferred commit therefore snapshots the selection when its event fires (the selection-cache revision plus the `state.selection` array identities, so direct assignments count too) and re-selects only while that snapshot still matches, and it only clears the armed state while it still describes the field being committed.
- **A field that is already open is never re-opened.** Both `dblclick` branches check for it — the weight-cell one always did, the node-label one did not. Re-opening a label editor looked harmless because the field kept showing the same text, but it clears the field's draft mark, and a label editor that a rebuild restored gets its text programmatically, so no `change` ever reports the draft: the blur then found nothing to commit and the typed label was discarded (`Alpha` reverted to `E`). Returning early also leaves the browser's own double-click word selection intact.
- **An editor opens on the model, and a gesture flushes the commit it deferred.** Promotion seeds the field from `currentMatrixCellText` / `label || id` rather than from the DOM, which lags the graph by up to 60 ms (the debounced rebuild) — double-click a cell right after Ctrl+Z and the cell text is still the pre-Undo value. Within one gesture the lag is worse: clicking a node's *column* label while its *row* label blurs opens the second editor in the same task the first commit was deferred to the end of, so it used to be pre-filled with `A` while the graph already held `Alpha`, and the next keystroke anchored that stale text as a draft which the restore replayed over the commit (`Alpha` + `X` → `AX`). Label commits therefore register in a flushable queue that `beginLabelEdit` drains before reading the model; the microtask then finds nothing left to do. Weight-cell commits stay purely deferred — they end by demoting the field, and demoting inside the pointerdown task is what the deferral exists to avoid.
- **The tables are their own grid.** The matrix and the edge list separate every value with
1px cell borders, so the widgets inside them draw no boxes of their own: the order badge,
the move/reorder buttons and every edge-list input and select sit transparent on the grid
at rest (the borders stay 1px, only transparent, so unboxing shifts nothing), hint with a
background on hover and draw the accent ring on focus; a selected edge keeps its accent
border, and the editing cell editor keeps its opaque background so the hidden width
placeholder under it cannot ghost through. The locked node-label inputs were already
transparent for exactly this reason.

## CSV is a configurable, lossless app format

CSV has no rigid schema (RFC 4180 is informational), so the app defines its own dialect. **The familiar table always comes first and is byte-for-byte unchanged.** That means a full export opens in Excel/LibreOffice with the Nodes, Edges or adjacency-matrix grid displayed correctly. The extra `#GEP-CSV` rows do appear underneath it, though, as more rows/columns — they are ordinary CSV, not a spreadsheet comment — so a full export is not a clean rectangular grid-only file.

**Choose what to keep at export time.** Every CSV export preview has a contents fieldset:

| Checkbox | Section written |
| --- | --- |
| Visible table (always checked/disabled) | the familiar Nodes / Edges / Matrix CSV table |
| Title, counters & view | `meta` (`key,value`) |
| Settings & styles | `settings` (`key,value`), including type styles and pending defaults |
| Graph custom values | `graphCustom` (`key,value`) |
| Custom attribute definitions | `attributes` (one column per definition field) |
| Nodes | `nodes` (one column per node field, including `custom` maps) |
| Edges | `edges` (one column per edge field, including tri-state direction and `custom` maps) |

All six sections are checked by default for Matrix CSV too, so an unedited all-sections export → import round-trip (file, clipboard copy/paste, or the preview's Import button) is lossless: nodes, edges, tri-state direction, labels, weights, styles, ids, custom attribute definitions/values, settings, title and counters all come back intact. Tests compare every CSV round-trip against the native JSON export. Column sets come from the union of record fields, and values are JSON in CSV cells, so types **and** field presence survive (`""` is a stated empty string; an empty cell means the field was absent). The current version and section markers are three-cell rows carrying a per-export `gep-…` nonce, so marker-like labels, weights, custom keys and quoted newlines cannot split the appendix; two-cell marker rows from the previous build remain readable.

**For a spreadsheet-clean adjacency matrix**, uncheck all six sections. The export then contains only the visible table: no marker rows, no extra columns below the grid, no clutter in Excel/LibreOffice. It imports as a partial/legacy CSV. The copy-to-clipboard buttons keep the all-sections default; use the Export preview for the configurable output.

**Keeping only some sections produces a patch.** Importing such a file applies just the included parts to the current graph and leaves everything else unchanged; the global Append setting is ignored for those files because appending the host document back into itself would duplicate it. The normal sanitizer still applies (for example, edges whose endpoint ids disappear after a nodes-only patch are dropped). Use every section for an exact whole-document copy.

**Partial / foreign CSV files without an appendix** still use the legacy readers:

- Nodes CSV replaces the nodes and drops the old edges; Edges CSV replaces only the edges (nodes, styles and background kept); Matrix CSV replaces only the edges (nodes kept). The file-import confirmation names exactly which part is replaced.
- The **Matrix CSV grid alone** stores only weights between labelled nodes. An undirected or mutual edge is written into **both** mirror cells so the connection reads from either end — the same bytes as two opposing directed edges. No reader can infer which was meant, so Data → Import / export → **Matrix CSV import interpretation** makes the choice explicit for these files:
  - **One edge per cell** (default, historical): every populated cell produces one edge per weight; symmetric pairs stay two edges and the toast warns about the ambiguity.
  - **Mirror cells are one undirected edge**: a symmetric pair with identical weight lists collapses into one undirected edge per weight. Pairs with differing weights, one-sided cells and self-loops keep the literal reading; one-sided cells follow **Style → New edge defaults → Direction**. This reading also merges genuine two-way directed pairs — unavoidable for a file with no direction column.

Editing the export-preview text turns it back into a plain CSV: the appendix is dropped on Import so the user's edits actually take effect, and the note updates as you type or as the checkboxes change. A marker with no recognizable sections reports an error instead of wiping the graph. JSON remains available as a compact single-format alternative, but it is no longer required for an exact round-trip.

A failed or aborted `FileReader` read reports an actionable message (re-select the file, or paste its contents into the export preview) rather than leaving the user with a silent no-op.

## Source layout

The TypeScript files are deliberately ordered in `tsconfig.json`. They form one typed program and are wrapped in a private IIFE in the final HTML, preserving the original application's shared runtime state without exposing implementation globals.

| File | Responsibility |
| --- | --- |
| `src/app/00-i18n.ts` | English/Russian translations and language switching |
| `src/app/10-core.ts` | Types, state, validation, history, shared utilities, and the in-app dialog system |
| `src/app/20-rendering.ts` | SVG, matrix, edge-list, and selection rendering |
| `src/app/30-graph-editing.ts` | Graph mutations, selection, sorting, and matrix editing |
| `src/app/40-interactions.ts` | Pointer, drag, pan, zoom, and canvas selection behavior |
| `src/app/45-gizmo.ts` | Position-only translate/rotate/scale/rect selection gizmo |
| `src/app/46-dot-core.ts` | DOT parsing core (used by the 50-import-export module): tokenizer, string handling, round-trip-safe statement extraction |
| `src/app/50-import-export.ts` | JSON, CSV, DOT, and GraphML import/export |
| `src/app/60-algorithms.ts` | Graph algorithms and automatic layouts |
| `src/app/70-controls.ts` | Style controls, presets, camera controls, and hotkeys |
| `src/app/80-ui.ts` | Event wiring and responsive view controls |
| `src/app/90-bootstrap.ts` | Application initialization |
| `src/app/types.d.ts` | Shared graph and UI type declarations |
| `src/core/graph-patch.ts` | DOM-free graph change core used by clipboard paste and reusable by server updates |
| `src/app/00-compat.ts` | ES2020 fallbacks for the ES2023 array helpers used in the app |
| `src/template.html` | Semantic page markup |
| `src/styles.css` | All application styles |

`index.html` is generated and should not be edited directly.

`src/core/graph-patch.ts` is the reusable change-application layer. `GraphPatchCore.applyExactPatch(target, patch, options)` mutates a plain graph-shaped target (`nodes`, `edges`, `nextNode`, `nextEdge`) and reports what changed; it has no DOM, clipboard, history, or toast dependencies. `GraphPatchCore.applyServerChange(target, change, options)` wraps it with idempotency and monotonic-revision checks for server-delivered patches. Its patch shape and built-in entity fields are validated before anything is mutated: malformed fields, missing IDs and duplicate IDs return `invalid`, leave the target untouched and are not acknowledged, so a corrected change can be resent at the same revision. Server changes enforce the editor's 3,000-node and 8,000-edge limits even when options are omitted; callers may choose stricter limits but cannot raise those ceilings. Its result distinguishes `applied`, `partial`, and `rejected`: work affected by the document caps is not acknowledged, so the caller can retry it when capacity returns. Clipboard paste in `src/app/30-graph-editing.ts` is a thin adapter that validates clipboard data, calls the same core, then performs selection/history/render/save side effects. The core is an ordinary TypeScript module: `import { GraphPatchCore } from './src/core/graph-patch.js'`. After `npm run build:core` (also included in `npm run build`), JavaScript and declarations are available at `dist/core/graph-patch.js` and `.d.ts`, or through the package subpath `graph-editor-pro/core`. The offline HTML bundles this same implementation inline. Server custom values must use canonical keys backed by definitions in `target.customAttributes`, with values that survive the loader unchanged; absent definitions and values that the loader would coerce are rejected before mutation. Validation uses the loader's shared coercion policy, so stated empty and other verbatim numeric/boolean strings remain valid. Server patches apply supplied node order changes, while exact clipboard paste preserves the existing nodes' order; other core callers can opt in via `applyExistingNodeOrder`. Legacy `directed` updates synchronize the authoritative `direction` field.

## Paste in place

`Ctrl+V` (⌘+V) pastes the copied nodes and edges with an increasing offset and never reuses the copied ids. The **Paste in place** button and `Ctrl+Alt+V` / `Ctrl+Shift+V` (⌘+Option+V / ⌘+Shift+V) paste the same payload at its original coordinates instead. Ids already present in the document are updated in place — only fields carried by the clipboard change, so unrelated node/edge data, custom values and omitted coordinates survive — while missing ids are created at their copied coordinates. Repeating an in-place paste is therefore idempotent rather than piling up clones. A readable system-clipboard payload wins over the in-memory copy once the latest local write succeeds; a failed or pending write leaves the local copy authoritative until the system clipboard actually changes again (a newer cross-tab copy). Clipboard fields are normalized with the loader's validation rules; edges resolve through the untrimmed raw node IDs and uncarried endpoints must match a host ID exactly. Both paste modes stop at the same 3,000-node / 8,000-edge limits as the loader — entities dropped there never leave orphan custom definitions behind, and definition changes are undoable.

## Moving selections: transform gizmos

In Select mode, a selection that contains nodes (or only edges — their endpoints are used) gets a transform gizmo: handles drawn around the selection on the canvas, a floating toolbar row above the selection tools, and a matching **Transform gizmo** section in the Edit tab with a live status readout. **Every gizmo tool rewrites only node `x`/`y` positions.** Node widths, heights, shapes, colors, labels — all visual parameters of the individual parts — are never touched; the node bodies simply ride to their new spots and connected edges follow through the same live-edge fast path as an ordinary node drag.

| Tool | Handles | What it does to the selected positions |
| --- | --- | --- |
| Translate (`1`) | centre dot, X arrow, Y arrow | Free move, or move constrained to one axis. Existing snap settings (grid, Snap X/Y) apply to the gizmo origin |
| Rotate (`2`) | ring around the pivot | Rotates positions around the pivot. `Shift` snaps to 15° steps |
| Scale (`3`) | X/Y end squares, centre square | Scales positions from the pivot per axis (`Shift` = uniform from an axis handle) or uniformly from the centre. Node sizes do **not** scale |
| Rect (`4`) | bounding-box corners/edges, centre | Stretches positions with the selection's bounding frame: the dragged side follows the pointer, the opposite side stays anchored. `Alt` stretches from the centre, `Shift` keeps the aspect ratio |

The **pivot** defaults to the centre of the selection's bounding box. In Rotate/Scale (and Rect) it is the small white dot: drag it — it snaps onto node centres — to rotate or scale around any point, and double-click it to reset. It resets automatically when the set of selected nodes changes.

A numeric readout (delta, angle, factor, or frame size) follows the drag on the canvas and in the status pill. `Esc` cancels a gizmo drag and restores the exact pre-gesture positions; a committed drag is a single undo step. Arrow keys nudge the selection (grid step while snap is on, otherwise 1 unit; `Shift` multiplies). `G` (or the *Show transform gizmo* checkbox in the Edit tab's Transform gizmo section) hides the gizmo when its handles would get in the way. The digit/`G` bindings are remappable like the other hotkeys.

Implementation notes: `src/app/45-gizmo.ts` owns the gizmo's preferences, rendering, gestures and keyboard nudging; the rest of the app only keeps render/selection notifications, pointermove/pointerup routing, and button/hotkey wiring. The active tool and show/hide choice are browser UI preferences in `localStorage` (`graph-editor-pro-gizmo`), not document data — they never enter exports, autosaves or undo snapshots, and toggling visibility cannot create a history step (legacy autosaves that still carry the old document fields are migrated once on load). The gizmo lives in its own `#gizmoLayer` inside the camera scene, above the nodes, and is rebuilt only when its signature (tool, selection ids, pivot, bounds, screen-pixel size, drag state) changes. Handles are sized in world units per screen pixel, so they keep a constant on-screen size at any zoom; only handle shapes take pointer events (lines and the rotate ring are stroke-only), so the frame never blocks the nodes under it. During an ordinary group drag the whole gizmo follows with a single transform write on its root instead of a rebuild.

## Custom properties

User-defined **custom attributes** (the Data tab → *Custom attributes* section) can carry values, not just definitions. Every attribute has an ID, a scope (`graph`, `node`, `edge` or `all` — one definition covering graph, nodes and edges, the analogue of GraphML `for="all"`) and a GraphML type (`boolean`, `int`, `long`, `float`, `double`, `string`), and the matching editors appear where the value lives:

| Scope | Where values are set and viewed |
| --- | --- |
| `graph` | Data tab, **Graph values** block under the definitions |
| `node` | Selection panel in the Edit tab (single selection, or applied to all selected nodes); **Node placement** section for values pending application to new nodes |
| `edge` | Selection panel in the Edit tab (single selection, or applied to all selected edges); **New edge defaults** section for values pending application to new edges |
| `all` | One definition stored once; the graph, node and edge editors (and the pending-default editors) all show and edit its value under the same id |

New nodes/edges created afterwards inherit the pending values from **Node placement** / **New edge defaults**; the pending values are stored on settings (`nodeCustom` / `edgeCustom`), so they ride history (one undo step per edit), autosave and the sanitizer like every other new-element default. The Selection section is the first section of the Edit tab, so the property grid of the current selection is always one click away.

Values follow the definition's type: a tri-state select for `boolean` (unset / true / false), a free-text numeric field for the numeric types (rejected with a toast and reverted to the stored value if it is not a number — text inputs with `inputmode`, not `type="number"`, so garbage can never masquerade as "empty"), and a plain text field capped at 1000 characters for `string`. An empty field unsets the value (except multi-select text/number fields, where empty means *keep*, matching the other multi-edit inputs); values for a definition that is deleted are stripped, and renaming an ID moves the values with it. Setting a value is one undo step.

Persistence and interop:

- **JSON** (the native format) and **GraphML** carry both definitions and values, including values on the graph element itself. The GraphML importer coerces `<data>` payloads to the declared types; QVGE files with custom keys round-trip with their values intact.
- **Stated empty values:** an explicitly empty (or whitespace-only) `<data>` on a custom key is a *stated* value, not an absence — it is stored, survives save/load/export, and suppresses the key's declared `<default>` on import. Presence, not truthiness, decides. In the property editors themselves, an empty field still means *unset* (see above).
- **DOT** and the three CSV exporters intentionally carry only their documented subsets and skip custom properties.
- Append-mode imports merge the carried definitions with the current document in a fixed order: an exact id **and** scope match merges for free (current wins), and an `all`-scoped definition covers a narrower incoming pair the same way; the property already imported under another id is **reused** — matched by its recorded `attr.name` provenance — so re-importing the same foreign file never duplicates it; an id taken by a *different* property mints a fresh id with the carried id recorded as provenance, and the carried values are rebound to the resolved id — two files that merely share a key id never silently merge values. Definitions beyond the 2000-definition cap are skipped with a toast. Graph-scope values merge with the imported values taking precedence. History snapshots, autosave and the sanitizer all round-trip the values; unknown attribute IDs and anything but `string|number|boolean` scalars are dropped/coerced at the door.
- Copy/paste/duplicate deep-copies the value maps, so a pasted selection never shares custom property state with the original.
- Pending **new-element** defaults (`settings.nodeCustom` / `edgeCustom`) are sanitized against their own scope's definitions, stripped when a definition is deleted and migrated when it is renamed — same rules as stored values.
- **Limits and coercion:** up to 2000 values per element (matching the definition cap) and 1000 characters per string. Out-of-range or otherwise unrepresentable numeric input (e.g. the int32 minimum, or a 64-bit long beyond JavaScript's safe-integer range) is stored as the exact text, never silently clamped — the same rule applies to a stated fraction typed into an integer-typed property. Changing a definition's type migrates every stored value; values that cannot be represented are dropped (and a toast says how many), with undo restoring them.
- **GraphML interop details:** custom `<data>` is matched by exact key id, never by (case-normalised) `attr.name`, so case-distinct custom ids round-trip without overwriting built-ins or each other; graph-scope `<data>` no longer sees descendant node/edge elements; and a `<default>` on a custom `<key>` is applied to elements without explicit `<data>` on import. Every definition key the exporter writes carries a `qvge:kind="custom-attribute"` marker (and the `<graphml>` root declares the writer). In our own files, a marked key always comes back as a definition and an unmarked key is a definition exactly when its id lies outside the built-in block; a foreign file that reuses a built-in key id feeds the built-in field it names (case-insensitively) instead of appearing as a definition, and a foreign key with a non-built-in name imports as a new custom attribute. A definition whose id collides with a built-in key id is exported under a numbered suffix with its own id riding in `qvge:id`, so it comes back without drifting, and a re-created definition records `qvge:origin` so the next import rebinds the foreign property instead of minting a duplicate. Adding or appending definitions (append-mode import included) immediately repaints the selection panel, the graph values block and the new-element default editors.
- **No id is reserved.** A definition may legitimately look like a built-in (`direction`, `arrowSize`, …): ids are never rejected, and the export-side de-collision above means a document carrying one round-trips unchanged. The custom keys live in their own namespace (the `qvge:` marker and a writer declaration on the root), so they cannot collide with a built-in key; a legacy `qvge.custom.` prefix from the previous build is still recognised on import. Documents saved before any of this existed load without migration.
- **Definition cap and `__proto__`:** the editor holds at most 2000 attribute definitions. Reuse (an exact id+scope match, or a provenance match) runs before capacity accounting and never consumes it, so re-importing the same file never exhausts the budget; only genuinely new definitions count against the remaining capacity, and anything beyond the cap is skipped with a toast, never silently dropped on reload. Custom ids are never rejected; values are stored in own-key maps, so a property literally called `__proto__` is stored, cloned, rendered and round-tripped like any other.
- **Type changes:** switching a definition to `long` (or `int`) keeps values the JS number line cannot hold exactly (e.g. `9223372036854775807`) as the exact text instead of dropping them, matching the input and import paths.

## Build and safety guarantees

The build fails if any of these guarantees are broken:

- TypeScript does not type-check.
- Inline JavaScript is syntactically invalid.
- The output has anything other than one inline script and one inline style block.
- A script, stylesheet, media resource, CSS import, or remote CSS URL is external.
- Runtime network APIs such as `fetch`, `XMLHttpRequest`, `WebSocket`, or `EventSource` appear in the output.
- Static markup contains duplicate element IDs.

Current verification: `npm run check` is typecheck-clean and passes **649/649 tests**; the rebuilt single-file `index.html` is **1,204,779 bytes** and the static-output gate passes. Headless Chromium passes **17/17** browser tests. `tests/camera-render-regressions.test.mjs` has 26 regressions, including the 1422×588 vertical/horizontal extreme Fit cases and original-midpoint label placement for partially clipped edges.

Runtime data is also validated before use. Every import path — JSON, GraphML, DOT, edge/nodes/matrix CSV and the clipboard — runs through the same sanitizer, so all of them share the 3000-node / 8000-edge caps, labelled-field bounds, colour/shape/stroke validation and dangling-edge removal (a CSV import that exceeds a cap says so in the toast instead of silently building an oversized document that shrinks on the next reload). IDs are normalized and deduplicated, numeric/style values are clamped, unsafe map keys are isolated in prototype-free records, and required DOM elements fail with a descriptive error instead of causing a later null dereference. DOT parsing strips comments only where DOT defines them (a leading `#` on a line, `//` and `/* */` outside quoted strings), so hex colours and labels such as `C#` survive; the line scanner accepts LF, CRLF and lone-CR endings, and string unescaping is a single pass so `\n` (newline), literal `\n`, quotes and trailing backslashes all survive. DOT export/import round-trips labels, positions, colours, node types, node order, label typography and the six shapes (hexagon as `hexagon`, triangles as `triangle`/`invtriangle`, and QVGE's `triangle2` read as the same inverted triangle); positions are written in inches with the y axis flipped, the unit GraphViz and QVGE both use, so `width`/`height` and `pos` agree, and an incoming `inputscale` is honoured as points; a QVGE `xlabel` is read as the label and `fontcolor`/`fontsize`/`fontname` as its typography, while `label` never silently becomes an edge's weight; quoted strings and HTML-like labels may embed brackets and tags (`label="arr[0]"`) without confusing the attribute-list parser, and stacked attribute lists (`graph [a][b]`) merge on import. CSV export prefixes formula-like cells with an apostrophe and doubles it when the value already starts with one, so imports restore every label byte-for-byte, including text such as `'=1+1`. CSV node rows keep the order column exactly as written — `0` is an order, not a missing value — and fall back to the row position only when the cell is empty. Autosave is flushed on `pagehide`, and a failed write (full or unavailable storage) reports itself instead of failing silently.

## Dialogs and keyboard

Destructive and text-entry actions (clearing the graph or the matrix, replacing the document with an import or the sample graph, naming a preset, the double-click node-label and edge-weight editors) never call the browser's blocking `prompt`/`confirm`/`alert`. `showDialog()` in `src/app/10-core.ts` opens a native `<dialog>` modal, so the browser supplies the inert background, focus containment, top layer and platform dismissal; without `showModal()`, prompts and Style Presets use a document-level focus trap. Clicking a heading does not let the next Tab or Shift+Tab reach the background. The title is wired through `aria-labelledby`, Escape and backdrop-click cancel, and focus returns to the triggering control on close. The buttons are translated (`dialog_ok`, `dialog_cancel`, `dialog_confirm_title`) and the text field opens focused with its value selected, so a double-click rename is type-and-Enter. Prompts and the presets dialog own the keyboard: graph shortcuts such as undo and delete stay inert, and Escape dismisses only the topmost dialog. The notification region moves inside presets while it is open, so feedback stays visible and accessible in the modal. Import failures and oversized-file notices use the `aria-live` toast stack instead of an alert. The stack normally holds four messages; a new arrival never evicts a message being hovered or focused.

## Performance design

Navigation is a **single paint system**: one camera surface, `#cameraLayer`, an SVG `<g>` inside `#graphCanvas`, moved by one absolute `transform` matrix (space-separated SVG `matrix()`, in user units). The root `viewBox` is a fixed world reference frame (`-500 -330 1000 660`, `xMidYMid meet`) installed once and never rewritten during a gesture. A preview and a commit are the same write — the preview *is* the camera, committing only records it in `state.viewBox` — so no frame can mix two cameras and there is no handoff. Keeping the matrix **inside** the SVG is what lets every world point be painted: an HTML wrapper transformed around the `<svg>` can only move the already-clipped viewport, so nodes and edges outside the reference frame silently disappear at zoom/pan. The stationary `div#gridLayer` carries only the background colour; the grid itself is two persistent world-space `<path>`s inside `g#gridLines` in the camera scene, so it rides the very same matrix as the graph, cannot expose an unpainted edge, and cannot re-pitch or re-phase on a commit. `#cameraLayer{will-change:transform}` keeps that group composited, so a camera change is one attribute write rather than a full scene repaint. Measured on headless Chromium at 1200 nodes (two runs, `scripts/perf-bench.mjs`): pan **3 dropped frames / 16.8 ms p95** and wheel **6 dropped frames**, against 4 and 19 for the pre-PR30 baseline. Across every scaling path (wheel, zoom buttons, pinch, `fitView`, and window resize), zero SVG elements are torn down or recreated: `fitView` / `resize` re-apply only the camera instead of reconciling `#nodesLayer` and `#edgesLayer`, and `#gizmoLayer` updates cached per-tool handle subtrees in place.

**Do not add a second camera surface, and do not wrap the SVG in a transformed HTML camera.** Two separately-transformed surfaces (the `#cameraStage` era, commits `7f09230`/`af90851`/`aa081b7`/`12df425`) update on different clocks; two DOM writes can never be atomic and that desync flashes one wrong frame at gesture end. A single wrapper `<div>` around the `<svg>` is not a fix either: it transforms the SVG viewport *after* the root `viewBox` has clipped the scene, so far nodes and edges vanish, and a viewport-sized CSS-gradient grid inside it either crops during a pan or re-phases at the commit. Nor should a preview write a *relative* delta from the last committed camera: that puts the graph in the wrong place for the whole preview. The speed comes from the compositing hint on the SVG group and one absolute matrix, never from splitting the camera.

The world-space grid paths are regenerated only when the visible world range leaves their decimated apron or the integer decimation step changes; panning and wheel previews normally write nothing but the one camera matrix (zero `childList` mutations). Lines are always integer multiples of the configured grid cell in world units, with `vector-effect:non-scaling-stroke`, so they stay world-locked at every zoom, including zoom-outs far past the fixed reference frame. Real-browser A/B against the pre-PR30 build gives identical camera matrices, node/edge positions and grid coverage at rest, mid-pan, mid-wheel, and after every commit.

**Data preservation and coordinate safety.** World coordinates are never rewritten at ingestion or autosave: node positions and the camera centre stay exactly as loaded/typed, including values beyond ±1e9. Chromium/Skia clamps SVG geometry and transform numbers above ~2^25 (33,554,432), so a floating render origin snapped to the camera centre in 1e6-unit steps rebases every SVG attribute — camera matrix, nodes, edges, grid paths, selection drafts and gizmo handles — onto it. When a snap boundary is crossed, geometry is rebased **in the same task** as the camera matrix (never on a later animation frame). Rather than cap the world camera, a power-of-two **render-space scale** multiplies every SVG number; the inverse is written on `#sceneLayer` as a product of small `scale()`s (each ≤ 2^20), and the camera matrix stays in true world units. That keeps a 1422×588 Fit of a 30,000,000-unit vertical span and a 60,000,000-unit horizontal Fit untruncated while every path/transform number remains below Skia's limit. A 60,000,000×60,000,000 camera uses `scale(4)` with a 0.25 render scale; a 1e20-unit camera uses three small factors and loads without a hang. At normal zoom the visible node shape is the hit target: the inert `.node-hit` circle stays inside the smaller body dimension, so a 300×10 rectangle cannot select from 80 px away. Only at sub-pixel zoom-outs is a visible ~7 px dot enabled, and centre-hit mode uses that same effective radius. Nodes beyond the scaled safe window are skipped in the DOM only; long edges are clipped with Liang–Barsky instead of being discarded, so a crossing segment still renders and hit-tests. Label/weight placement comes from the edge's **original world midpoint**, not the clipped segment: an off-screen midpoint suppresses the text, weight and plate instead of painting them near the canvas centre, while a visible midpoint puts them at their true position. Fully clipped edges still suppress their arrow and selection accent. Grid paths are capped to the scaled safe square, enumerate a bounded local `i` under a 4,000-segment cap and a `GRID_INDEX_LIMIT` guard instead of an absolute `k++`, and a BigInt remainder keeps lines locked to world cell boundaries even when the 1e6 snap is not divisible by the configured grid step. `currentCamera()` remains the single active-camera accessor for wheel zoom, pan and pinch previews; grid-style handlers default to it and `applyCamera()` adopts it before an unrelated re-render, so changing a grid colour mid-gesture cannot recompute the grid from the stale committed camera.

**Performance trade-off.** An independent two-run, 1,200-node Chromium measurement against the PR #33 base reported about **3.1 ms/update** of wheel style/layout on this PR versus **0.2 ms** on that base; a rerun with `scripts/perf-bench.mjs` measured **2.1–2.5 ms** versus **0.1 ms**. The lower number comes from that base's CSS-gradient grid and wrapper `DIV` transform, which avoid SVG style/layout but also produce the known clipping, blank-grid and wrong-preview defects this PR fixes. It is a correctness/performance trade-off, **not** an equivalent-correctness comparison. Against the pre-PR30 in-SVG baseline (which had the same kind of camera), the harness reports comparable per-update style/layout (2.5 ms vs 2.3 ms) and fewer dropped wheel frames (14 vs 23); final floating-origin reruns report 1.1–1.7 ms versus 1.2–2.1 ms, with dropped wheel frames varying from zero to two on either build across runs (no consistent frame-pacing advantage).

`scripts/perf-bench.mjs` measures all of this on a real headless Chromium (`scripts/browser-setup.sh` provides the browser): it drives 60 Hz input into pan and wheel gestures and reports renderer task/script/style/layout time, the per-camera-update style+layout cost, frame pacing and the camera DOM writes, per graph size. Pass `--build name=directory` twice to compare two revisions in one session.

`scripts/bench-drag.mjs` does the same for the two ends of a node drag — press and release — which are the moments a drag feels sticky. It times each handler, then keeps recording animation frames for 600 ms after the release, so work that was merely pushed off the release (a queued render pass, a snapshot write) still shows up as a frame gap. `--graph hub` drags the centre of a star instead, i.e. a node with more edges than the live-drag budget.

Beyond navigation, the hot interaction paths are engineered so their cost tracks *what changed*, not the total graph size:

- **Indexed lookups.** `nodeById`/`edgeById` are lazily rebuilt hash indexes, so selection sync, drag geometry, and algorithm traversals stay O(1) per lookup regardless of graph size.
- **De-duplicated DOM writes.** Every attribute/class write on rendered graph elements goes through small `setAttr`/`toggleClass` helpers that skip the DOM when the value is unchanged, so a render pass that changes nothing writes nothing.
- **Delta selection sync.** Selecting an item touches only the elements whose selection state actually changed (the previous selection is mirrored), instead of re-toggle-walking every node and edge.
- **Per-pass visual caching.** Merged node/edge style objects and node radii are computed once per render pass and reused across edges and drag frames, eliminating thousands of short-lived allocations per frame.
- **Selection accents that follow the geometry.** A selected node carries a scaled copy of its own shape, a selected edge a wider copy of its own path plus a larger copy of its arrowhead triangle. The elements exist only while selected, the edge accent reuses the path string the line was just given (no outline of the edge shape is derived), and the live-drag writer that re-points the edge re-points the accent in the same frame — measured at +2 attribute writes per selected edge per frame on a 300-edge hub drag (429 total).
- **Bulk selections that cost one write per edge, not two elements.** Accents are the look until the selection gets large: a region select can put most of the graph in the selection, and a rect over a 1,500-node/4,388-edge document selects ~2,500 edges, i.e. the two accent elements each would create (~5,000 elements) inside the release handler. Past 320 selected edges the accents are not created and selected edges are drawn in the accent colour instead, so the highlight still covers exactly the selected edges, the selected ids keep their `selected` class, and nothing in the hit-test, drag or panel path reads accents. Measured on that document (rect select over the whole canvas, 792 nodes and 2,493 edges selected): the release handler drops from 35.0 ms to 15.2 ms and the stall through the following frame from 131 ms to 81 ms; with the accents skipped entirely it is 10.6 ms and 70 ms, so the remaining cost is the selection sync itself. Node rings are one element each (~3 ms per 800) and are never budgeted out, so a large node selection keeps the normal ring look. The look is chosen once per update, so a frame can never be half outlined and half coloured, and releasing the selection hands every edge back its own colour.
- **Gesture-scoped re-rendering.** A click that does not move anything performs no full render pass at all, and a drag whose connected edges (up to 2000) were patched live during the gesture needs no re-render on release.
- **Drag ends that stop at the gesture.** Press and release both used to run work that could have waited, in the task the pointer is waiting on. The press rebuilt the whole selection panel (a few dozen controls, listeners re-wired) before the node could follow the cursor; it now marks the panel dirty and renders it on the next frame, which the canvas never looks at. The release serialised the entire document for the undo stack; that snapshot now runs at idle time after the release frame, and every input that could edit the document — a pointer press, a key, a wheel, or any other history push, undo or redo — flushes it first, so an undo pressed straight after a drag still restores the pre-drag position. Both are measured on the drag bench: on a 3,000-node graph the press handler drops from ~6 ms to ~1 ms and the release handler from ~10 ms to ~0.1 ms.
- **Frozen edges catch up in place.** Past the live-edge budget a drag cannot repaint its edges frame by frame, so they are left at their start geometry. The release re-points exactly those edges through the same in-place writer the live path uses, one frame later, instead of running a render pass over every node and edge of the scene: dragging the centre of a 2,500-edge star used to end with a ~90 ms stall, now with a ~70 ms one-frame catch-up that the release itself does not wait for. The correction path also covers keyboard nudges and gizmo drags.
- **One element query per page, not per render.** The selection sync renders the gizmo, whose tool buttons were looked up with a document-wide attribute query on every update — milliseconds on a large scene, inside every press. The static buttons are resolved once.
- **Same-task commits for immediate commands.** A command whose only visible effect is local geometry writes the canvas in the click's own task and lets the queued render pass confirm it. Flipping selected edges re-points each flipped edge through the drag-time writer (path, label/weight, arrowhead and selection accent), so the new direction is on screen in that frame instead of two frames later, behind the sidebar rebuild the queued pass carries on large graphs. Full-state operations (undo/redo, import, layout) keep going through the render pass, which owns the whole scene.
- **Frame-coalesced selection tools.** Brush/lasso/rect/line strokes sample every pointermove but run their hit test and overlay redraw once per animation frame; live brush selection defers the sidebar rebuild until the gesture ends.
- **Stable interaction paint.** `.fast-interaction` records gesture state but intentionally changes no filter, label, or shape paint property. The scene therefore keeps identical visual effects before, during, and after a drag; release cannot force a replacement SVG layer or flash a stale raster.
- **Zoom-adaptive grid.** The grid layer decimates to every k-th cell (an integer multiple of the configured grid) when zooming out would shrink cells below a readable on-screen minimum. Lines stay locked to world coordinates at every zoom level instead of drifting or desynchronizing from the nodes.
- **Bounded supporting views.** Large matrices and edge lists render behind configurable limits (defaults: 250 edge rows per page, matrices hidden above 90 nodes) independently of graph size. Both settings accept any positive integer, but the matrix has a hard rendering ceiling of 14,400 cells (120×120 nodes) regardless of how high the limit is set: an n×n grid costs n² DOM elements (cells render as lightweight `<td>`s and promote to an `<input>` only while edited — see *Editing the adjacency matrix*). Measured in Chromium on a 350-node document, a full 300×300 render takes ~5.8 s to paint, 150×150 ~1.6 s and 120×120 ~1.2 s, so the ceiling sits where the view stays usable. Larger matrices show as a `120×120 view of N nodes` (the note names the real graph size and the ceiling), with full data still available through paging, the edge list and CSV export.
- **Budgeted layout runs.** The force-directed layout is all-pairs, so its cost is O(iterations · n²); it now budgets pair work (≈17M interactions) instead of always running 180 passes, and the run yields to the browser every ~50 ms (`scheduler.yield()` with a `setTimeout` fallback) so input and paint are not blocked. The time budget is checked between rows of node pairs, not just between passes. Positions and endpoints are captured at the start; the result is applied in one undo step. An intervening document edit (such as typing a title), undo, or active drag discards the result without writing partial positions or history. Typing in a camera field does not interrupt the layout. Measured on 1,200-node-class graphs this keeps one click near a second (600 nodes: 613 ms for 94 passes, 1,500 nodes: 707 ms for 15 passes) and the toast says when the pass count was reduced. Circle and grid layouts are O(n) and unaffected.
- **Cheap element access.** Render passes walk the node/edge layers via linked-list traversal (`firstElementChild`/`nextElementSibling`) and read reflected `id` attributes rather than collection indexing or `dataset`, and id→element registries keep drag and selection paths off document-wide lookups. The parallel-edge lane cache rebuilds only when the edge array actually changes.
- **Per-edge geometry caching.** An edge's path depends only on endpoint positions, node radii, its parallel-edge lane, and direction; when none of those changed, the render pass reuses the previous path result instead of recomputing it. Dash-pattern strings are memoized per (style, stroke size).

### Comparison with draw.io (mxGraph)

The interactive-rendering model mirrors the mechanisms draw.io uses, verified against its source (`jgraph/drawio`, `src/main/webapp`):

| Mechanism | draw.io / mxGraph | This editor |
| --- | --- | --- |
| Panning | `mxGraph.prototype.panGraph` moves the canvas via a `transform` during the gesture; the view is revalidated once on release | One absolute `transform` on the SVG camera group carries graph and grid together during the gesture; release records the same camera above a fixed reference `viewBox` |
| Wheel zoom | `EditorUi.js` `lazyZoom` accumulates a `cumulativeZoomFactor`, previews with `mainGroup.style.transform = 'scale(f)'` anchored at the cursor, removes shape filters during the preview, and performs one real zoom after a debounce (`lazyZoomDelay` 20 ms / `wheelZoomDelay` 500 ms) | Cumulative preview as one absolute matrix on the composited SVG camera group (`0` SVG rebuilds per frame); the ~220 ms debounce only persists the camera, with in-place grid/gizmo updates |
| Indexed lookups | cells and view states are kept in `mxDictionary` hash maps | node/edge ids resolve through lazily rebuilt hash indexes |
| Drag feedback | `mxGraphHandler.updateLivePreview` repaints moved states and all connected edges live | connected edges follow drags live up to a 2000-edge budget, then freeze until release |
| Undo history | `mxUndoManager` caps at 100 entries (delta edits) | 100 entries plus a total-size cap, since this editor stores full-state snapshots |
| Off-screen culling | none — SVG clips at paint time | none by default, plus an optional order-based visible-range filter that removes non-visible nodes from the DOM entirely |

## Clipboard publication

Graph copies publish under an **origin-wide Web Lock**, held until `writeText`
settles. Tabs announce pending copy intents before waiting; a later copy can
recognize an earlier pending predecessor even if neither has reached the lock.
Ambiguous equal timestamps across tabs fail closed. Before a delayed publication,
bounded reads verify that the clipboard is still the pre-copy content or a
known predecessor. A changed, unreadable, or stalled clipboard keeps the copy
local and reports the failure. Lock waiting is cancelled after 30 seconds; it
never cancels or steals an active write.

**Different sites and downloaded instances do not share Web Locks or storage.**
A delayed write at one origin can overwrite a newer copy from another origin,
and a fresh tab cannot detect which clipboard item is newer. Graph pastes show
a warning rather than silently claiming that system clipboard ordering is
known. Clipboard-history items remain pasteable; the warning does not reject
them. Use a single origin or export/import JSON to avoid cross-origin copy races.

An in-flight marker guards against a tab disappearing while a browser write
might still complete. If it remains after a tab is lost, subsequent copies are
local only. To recover, close **all** Graph Editor tabs, completely restart the
browser, then reopen the editor and choose **Edit → Clipboard recovery**. The
confirmation explains why these steps are required; recovery refuses to clear a
marker while another same-origin tab holds the lock. Never confirm recovery
while an old write could still complete.

Without Web Locks or usable site storage, system graph publication is disabled
rather than risking unordered writes. The editor reports this separately from
an abandoned write: enable site storage or use a browser supporting Web Locks,
or export JSON and import it in the destination document. After a local-only
Cut, use Undo before exporting. Ordinary system clipboard paste remains
available, and the shared stamp registry is not used to reject restored history.
